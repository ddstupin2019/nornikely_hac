# КТО ТЫ И ЧТО МЫ ДЕЛАЕМ

Ты — старший инженер, реализующий систему «Фабрика гипотез» для хакатона Норникеля
(AI Science). Задача системы: из целевого показателя (KPI) + базы знаний (научная
литература, отчёты, данные экспериментов) генерировать ранжированный список
ПРОВЕРЯЕМЫХ научных гипотез — каждая с обоснованием, ссылками на источники,
механизмом влияния, оценкой новизны, рисков и потенциальной ценности.

Домен демо-данных — обогащение руд (флотация) на фабриках Норникеля. НО (критично):
закрытый тест жюри включает и ДРУГОЙ домен (металлургию сплавов). Поэтому система
должна быть ОБЩЕЙ для материаловедения и технологических процессов, НЕ заточенной
только под флотацию. Обогащение — один домен применения, архитектура универсальна.

# ЖЕЛЕЗНЫЕ ПРИНЦИПЫ РАЗРАБОТКИ (соблюдать в каждом блоке)

1. ПРОВЕРЯТЬ ГЛАЗАМИ. Никакую метрику/порог/формулу не принимать на веру. Сначала
   посчитать, потом ВРУЧНУЮ проверить на 20-30 реальных примерах: верно ли считает?
   нет ли ложных срабатываний? Пример опасности: взять порог совпадения гипотез
   без проверки → чинить симптом вместо реальной проблемы. Если расходится с ручной
   проверкой — ЧИНИТЬ ПРОВЕРКУ, не подгонять данные. Это правило №1.

2. ГАЛЛЮЦИНАЦИИ КАРАЮТСЯ ЖЁСТКО. Каждое фактическое утверждение в гипотезе обязано
   быть подтверждено источником (grounding). LLM склонна выдумывать правдоподобное
   (несуществующие параметры, ложные механизмы) — это «people-pleasing». Любой вывод
   модели, не подтверждённый корпусом, помечается как неподтверждённый или
   отбраковывается. Никогда не давать модели «дофантазировать» недостающее.

3. НЕ ЧЁРНЫЙ ЯЩИК. Каждое решение в коде — с комментарием ЗАЧЕМ. Каждый вывод системы
   — трассируем к источнику. Помечать: что факт (из данных), что оценка (мнение LLM).

4. СТРУКТУРНЫЙ ВЫВОД ВСЕГДА. Все LLM-вызовы возвращают строгий JSON по схеме.
   Невалидный/неполный JSON = перегенерация или отбраковка, НИКОГДА не «починка руками»
   с отсебятиной.

5. АТОМАРНОСТЬ И ЗАМЕНЯЕМОСТЬ. Каждый блок — отдельный модуль с чётким входом/выходом
   (JSON на входе, JSON на выходе). Блок можно заменить, не трогая остальные. Никаких
   скрытых зависимостей между блоками кроме объявленных интерфейсов.

6. ВОСПРОИЗВОДИМОСТЬ. random_state/seed фиксированы везде. Температуры моделей заданы
   явно в конфиге. Один и тот же вход → один и тот же выход.

7. ФИКСИРОВАННАЯ МОДЕЛЬ. Основная LLM фиксируется в config и НЕ меняется между
   версиями системы (мы измеряем вклад архитектуры, не разницу моделей). Модель:
   семейство Qwen (открытая, лицензия Apache для ≤35B, доступна в РФ, сильна в
   структурированном выводе и мультиязычности ru/en/zh). Конкретную строку модели +
   эндпоинт возьмёшь из config.yaml (заполнит оператор). Для ансамбля — см. блок B6.

8. КАЧЕСТВО ПЕРВИЧНО, ЭКОНОМИЯ ВТОРИЧНА. Организаторы ценят экономию ресурсов (малая
   модель при сохранении качества), но качество гипотез важнее. Не жертвовать
   обоснованностью ради скорости.

9. ПРОСТОТА ВНЕДРЕНИЯ. Меньше зависимостей, чётче структура. Перегруженное решение
   хуже простого работающего.

10. ЯЗЫК ДАННЫХ. Литература и данные — на русском, английском, китайском.
    Эмбеддер и промпты обязаны работать со всеми тремя.

═══════════════════════════════════════════════════════════════════════════
ПРОМПТ 1.1 — БЛОК B1: Парсер табличных данных (xlsx)
═══════════════════════════════════════════════════════════════════════════

Реализуй модуль b1_parse_xlsx.py.

КОНТЕКСТ ДАННЫХ: файлы вида «Хвосты_X.xlsx» — результаты анализа хвостов
обогатительной фабрики. Структура (проверено на реальном файле):
- Верх: потоки (поступило в переработку / отвальные хвосты), объёмы в СМТ (сухих
  метрических тоннах), содержания Элемента 28 (никель) и 29 (медь) в % и тоннах.
- Средняя часть: разбивка по КЛАССАМ КРУПНОСТИ (+125; -125+71; -71+45; -45+20;
  -20+10; -10 мкм) — доля класса, доля и тонны каждого металла.
- Нижняя часть (ключевая): для КАЖДОГО класса — минералогический анализ: в каких
  минералах сидит теряемый металл. Никель извлекается из раскрытого/закрытого
  пентландита (Pnt) и миллерита; медь — из раскрытого/закрытого Pnt/халькопирита(Cp).
  Из силикатной формы, пирита — НЕ извлекается.
- Строки «Извлекаемый металл» / «Неизвлекаемый металл» по классу = сколько из
  потерянного МОЖНО было бы извлечь. ЭТО КЛЮЧЕВЫЕ ЧИСЛА (см. ниже про ценность).

ВНИМАНИЕ: в файле есть ячейки #REF! (битые ссылки) — обрабатывай устойчиво,
не падай, помечай как отсутствующие.

ВХОД: путь к xlsx.
ВЫХОД (JSON):
```json
{
  "фабрика": "КГМК",
  "потоки": {"переработка_смт": ..., "хвосты_смт": ...,
             "никель_в_хвостах_т": ..., "медь_в_хвостах_т": ...},
  "классы": [
    {"класс": "-45+20", "доля_класса_%": ...,
     "никель_т": ..., "медь_т": ...,
     "никель_извлекаемый_т": ...,      // ← из строки "Извлекаемый металл"
     "никель_неизвлекаемый_т": ...,
     "медь_извлекаемый_т": ..., "медь_неизвлекаемый_т": ...,
     "минералогия": {"раскрытый_Pnt_т": ..., "закрытый_Pnt_т": ...,
                     "силикатная_форма_т": ..., ...}}
  ]
}
```

ЗАЧЕМ ЭТОТ БЛОК (объясняю, чтобы понимал важность): (а) это оживление «мёртвых»
архивов — боль заказчика; (б) числа «извлекаемого металла по классам» — ОСНОВА
объективной оценки ценности гипотез (в блоке B9 ценность = тонны извлекаемого
металла в целевом классе, взятые ИЗ ЭТИХ данных, а не выдуманные). Это наш козырь:
ценность в тоннах из реальных данных, не «мнение модели».

ПРОВЕРКА ГЛАЗАМИ (обязательно, правило №1): открой реальный файл, выведи распарсенный
JSON для 2-3 классов, и СВЕРЬ вручную с исходной таблицей — совпадают ли тонны,
правильно ли разнесён извлекаемый/неизвлекаемый металл по минералам. Покажи сверку.

ОБОБЩЁННОСТЬ: назови поля универсально где можно, но структура заточена под этот
формат данных — это нормально, парсер под конкретный формат. Для металлургических
данных закрытого теста будет другой парсер (или адаптация) — заложи возможность
（отдельный класс/функция под каждый тип таблицы）.

ПРОМПТ 1.2 — БЛОК B2: Парсер научной литературы (PDF/docx → чанки с provenance)
═══════════════════════════════════════════════════════════════════════════

Реализуй модуль b2_parse_docs.py.

КОНТЕКСТ: база знаний — учебники и статьи по обогащению/металлургии (PDF, docx),
на русском/английском/китайском. Размер до 150 МБ. Некоторые PDF могут быть сканами
(проверь: если текст не извлекается — пометь файл как требующий OCR, но OCR пока
НЕ реализуй, просто флаг).

ВХОД: путь к PDF/docx (или папке).
ВЫХОД (JSON, список чанков):
```json
[
  {"chunk_id": "...", "текст": "...", "книга": "Флотационные методы обогащения",
   "стр": 214, "язык": "ru"}
]
```

ТРЕБОВАНИЯ:
- Чанки 512-1024 токена с перекрытием ~100 токенов (чтобы мысль не рвалась на границе).
- КАЖДЫЙ чанк ОБЯЗАН нести {книга, страница} — это provenance для цитат. Без источника
  чанк бесполезен (галлюцинации караются — нужна точная ссылка). Это критично.
- Определяй язык чанка (ru/en/zh).
- Устойчивость: битый/пустой PDF не роняет процесс.

ЗАЧЕМ: это источник обоснований гипотез. В блоке B8 каждое утверждение гипотезы
проверяется против этих чанков, и цитата (книга+страница) идёт в вывод. Точность
provenance = защита от галлюцинаций.

ПРОВЕРКА ГЛАЗАМИ: распарсь 1 реальный учебник, выведи 3 чанка, сверь что текст
осмысленный (не каша), что номер страницы соответствует реальной странице PDF.

ПРОМПТ 1.3 — БЛОК B3: Индекс + Retrieval (RAG-слой, ЗАМЕНЯЕМЫЙ)
═══════════════════════════════════════════════════════════════════════════

Реализуй модуль b3_retrieve.py.

ВХОД: чанки от B2 (для индексации) + текстовый запрос (для поиска).
ВЫХОД: топ-k релевантных чанков с provenance и релевантностью.

ТРЕБОВАНИЯ:
- Эмбеддер МУЛЬТИЯЗЫЧНЫЙ (ru/en/zh): используй bge-m3 или multilingual-e5-large.
- Векторное хранилище: FAISS или Chroma (проще — Chroma).
- Функция index(chunks) строит индекс; функция retrieve(query, k) возвращает топ-k.
- ИНТЕРФЕЙС ФИКСИРОВАН: retrieve(query, k) → [{chunk, книга, стр, score}].
  Это критично: позже внутрь добавится ГРАФ знаний (гибрид RAG+граф), но интерфейс
  retrieve() НЕ изменится. Проектируй так, чтобы граф встал заменой начинки без
  переделки вызывающего кода. Оставь абстракцию (класс Retriever с методом retrieve).

ЗАЧЕМ: достаёт нужные знания из огромного корпуса под конкретную гипотезу/запрос —
и для генерации (B5), и для проверки обоснованности (B8). Это решение боли «данных
много, знаний мало».

ПРОВЕРКА ГЛАЗАМИ: проиндексируй реальные чанки, задай 3 запроса (напр. «влияние
крупности частиц на раскрытие пентландита»), выведи топ-3 результата, оцени —
релевантны ли? не мусор ли? Покажи.

ПРОМПТ 1.4 — БЛОК B4: Подготовка ограничений (оборудование, лимиты)
═══════════════════════════════════════════════════════════════════════════

Реализуй модуль b4_constraints.py.

КОНТЕКСТ: ограничения задачи — доступное оборудование (из регламентов/схем, которые
даны как PNG — транскрибированы вручную оператором в текст/JSON), бюджет, сроки,
нормативы (приходят в промпте от пользователя).

ВХОД: equipment.json (транскрибированный список оборудования) + текст ограничений
от пользователя (бюджет/сроки/нормативы).
ВЫХОД: структурированный блок ограничений для промпта генератора:
```json
{
  "доступное_оборудование": ["гидроциклоны", "классификаторы", "мельницы 3.3м",

  "бюджет": "...", "сроки": "...", "нормативы": "..."

```

ЗАЧЕМ (важно — это реализует принцип «реализуемость как ЗАКОН»): генератор должен
предлагать ТОЛЬКО реализуемое — с оборудованием, которое реально есть. Если система
предложит замену несуществующего агрегата — гипотеза бесполезна. Поэтому ограничения
идут в промпт генератора как жёсткие рамки. Реализуемость обеспечивается ЗДЕСЬ (на
входе), а не отдельной оценкой на выходе.

ПРОВЕРКА: выведи собранный блок ограничений, убедись что список оборудования полный
и корректный.

═══════════════════════════════════════════════════════════════════════════
ПРОМПТ 1.5 — БЛОК B5: Сборщик контекста (ЭКСПЕРТНАЯ ЛОГИКА ЗДЕСЬ)
═══════════════════════════════════════════════════════════════════════════

Реализуй модуль b5_context.py.

ЭТО КЛЮЧЕВОЙ БЛОК — здесь осмысленная подготовка контекста, не тупая склейка.

ВХОД: KPI/проблема (от пользователя) + профиль потерь (B1) + ограничения (B4) +
retrieval знаний (B3).
ВЫХОД: готовый промпт для генератора гипотез.

ЛОГИКА (экспертная, объясняю механику домена обогащения — но реализуй ОБОБЩЁННО):
  1. Из профиля потерь (B1) найти ПРОБЛЕМНЫЙ участок: класс крупности, где теряется
     МНОГО ИЗВЛЕКАЕМОГО металла (т.е. металла, который можно было бы достать, но он
     ушёл в хвосты). Пример: класс +71 мкм, 2101 т извлекаемого никеля в хвостах.
  2. Сформулировать направление: какое изменение нужно (в обогащении — изменить
     размер частиц через оборудование, чтобы раскрыть минералы; в металлургии —
     другое воздействие). ОБОБЩЁННО: «какой параметр процесса влияет на целевой KPI».
  3. Указать доступное оборудование (B4) — генерировать в его рамках.
  4. Приложить релевантные знания (B3) — чтобы генератор обосновывал, а не выдумывал.
  5. Приложить few-shot ПРИМЕРЫ требуемой конкретности (эталонные гипотезы:
     «замена насадок 12→8», «шары 120мм») — чтобы генератор держал планку
     конкретности, а не выдавал абстракции типа «улучшить классификацию».

ВАЖНО ПРО ОБОБЩЁННОСТЬ: закрытый тест жюри включает металлургию (не обогащение).
Логика «найти проблемный участок в данных → подобрать воздействие в рамках
ограничений → обосновать знаниями» — УНИВЕРСАЛЬНА. Не хардкодь «размер частиц» —
это пример для обогащения. Сделай логику «параметр процесса → влияние на KPI»
общей, а доменную специфику бери из данных.

ЗАЧЕМ: качество гипотез определяется качеством контекста. Мусорный контекст →
мусорные гипотезы. Здесь мы направляем генератор на реальную проблему (из данных)
в реальных рамках (оборудование) с реальными знаниями (для обоснования).

ПРОВЕРКА ГЛАЗАМИ: собери контекст для реального Примера 1, прочти собранный промпт —

ПРОМПТ 1.8 — БЛОК B8: Grounding-оценщик (обоснованность + цитаты)
═══════════════════════════════════════════════════════════════════════════

Реализуй модуль b8_ground.py. МЕХАНИЗМ ИЗ СТАТЬИ KnowHD (Xiong et al., IJCAI 2025).

ВХОД: одна гипотеза + доступ к retrieval (B3).
ВЫХОД: обоснованность (0..1) + список цитат {книга, стр} на каждое утверждение.

МЕХАНИЗМ (пошагово):
  1. Разбей гипотезу + её механизм на атомарные утверждения (claims). Пример:
     гипотеза «насадка 8мм раскроет пентландит в классе 40мкм» →
     claims: ["насадка 8мм даёт границу разделения ~40мкм",
              "в классе 40мкм есть закрытый пентландит",
              "уменьшение размера частиц раскрывает пентландит"]
  2. Для КАЖДОГО claim → retrieve(claim) из корпуса (B3).
  3. Entailment: спроси LLM «подтверждают ли найденные документы это утверждение?»
     → 1 (да) / 0 (нет). Верни для подтверждённых — цитату {книга, стр}.
  4. Обоснованность = доля подтверждённых = (Σ подтверждённых claims)/(всего claims).
  Формула: grounded(h) = (1/|C|)·Σ 1[context ⊨ claim].

ВАЖНО: этот блок НЕ МЕНЯЕТ гипотезу (защита от галлюцинаций!). Только оценивает и
прикрепляет цитаты/вердикт. Никакой правки текста гипотезы.

ЗАЧЕМ: это ось ОБОСНОВАННОСТИ (объективная — проверяется против корпуса) + источники
цитат (требование ТЗ). Научно доказано (TruthHypo): гипотезы с высокой
обоснованностью значительно чаще истинны. Это наш главный слой качества.

ПОРОГ: обоснованность < 0.5 → пометить гипотезу как слабую (отсев в B10).

ПРОВЕРКА ГЛАЗАМИ (критично, правило №1): возьми 20-30 пар (claim, найденный
контекст), и ВРУЧНУЮ проверь — верно ли entailment засчитал подтверждение? нет ли
случаев, где документ НЕ подтверждает, а модель сказала «да» (галлюцинация оценщика)?
Это самое опасное место. Покажи сверку подробно.

ПРОМПТ 1.9 — БЛОК B9: Оценщик осей (новизна, ценность-в-тоннах, риск)
═══════════════════════════════════════════════════════════════════════════

Реализуй модуль b9_score_axes.py. Три оси (обоснованность уже из B8).

ВХОД: гипотеза + профиль потерь (B1) + retrieval (B3).
ВЫХОД: заполненные оценки в контракте гипотезы.

ОСЬ НОВИЗНА [полуобъективная]:
  1. retrieve похожих решений из корпуса + из эталонных гипотез (если доступны).
  2. LLM-сравнение: «это решение уже известно/применяется в найденных источниках?»
  3. Новизна: идентично известному→0 (дубликат), вариация→0.5, принципиально новое→1.
  4. Верни ближайший аналог: «похоже на [источник], отличие: ...».
  НЕ косинус текста (перефраз даёт ложную новизну — Liu et al.). Только LLM-сравнение
  по смыслу.

ОСЬ ПОТЕНЦИАЛЬНАЯ ЦЕННОСТЬ [частично объективная — НАШ КОЗЫРЬ]:
  1. Определи целевой класс крупности гипотезы (из поля целевой_класс).
  2. Из профиля B1 возьми ОБЪЕКТИВНОЕ число: тонны ИЗВЛЕКАЕМОГО металла, теряемого
     в этом классе (поле никель_извлекаемый_т / медь_извлекаемый_т). Это ВЕРХНЯЯ
     ГРАНИЦА эффекта.
  3. Субъективный множитель: LLM оценивает, какую долю реально отыграть (0..1).
  4. Ценность = потолок_тонн × доля. ЧЕСТНО пометь в выводе: «потолок N тонн —
     ОБЪЕКТИВНО из данных; доля X% — оценка».
  Это отличает нас от конкурентов: ценность в ТОННАХ из реальных данных, а не
  «ценность высокая» (мнение). Для металлургии закрытого теста — аналог: брать
  количественный эффект на KPI из данных, если есть.

ОСЬ РИСК [субъективная, честно помечена]:
  - технический риск: вероятность что не сработает/навредит процессу (LLM + обоснование)
  - экономический риск: стоимость внедрения + стоимость/сложность проверки (LLM + обоснование)
  Пометь явно: это ОЦЕНКА, не факт.

ЗАЧЕМ: это обязательные поля выхода по ТЗ (новизна, ценность, риски). Ось ценности
в тоннах — ключевое конкурентное преимущество (объективность из данных).

тонны из правильного класса xlsx? Для новизны — согласен ли ты с вердиктом
«ново/известно»? Покажи.

ПРОМПТ 1.13 — БЕНЧМАРК (доменный + синтетический)
═══════════════════════════════════════════════════════════════════════════

Реализуй bench/domain_bench.py и проверь готовый bench/synth/.

ДОМЕННЫЙ БЕНЧМАРК (главное доказательство для жюри):
  Есть 4 кейса организаторов: пары (Хвосты_X.xlsx → Гипотезы_X.docx). Гипотезы
  экспертов — эталон (мозговой штурм: «насадки 12→8», «геометрия футеровки» и т.д.).
  Механизм:
    1. Подать системе xlsx кейса (гипотезы экспертов СПРЯТАНЫ — система их не видит).
    2. Система генерирует свой топ-N.
    3. МАТЧИНГ: для каждой экспертной гипотезы — есть ли похожая в выводе системы?
       LLM-судья: «гипотеза системы X = экспертная Y (то же воздействие)?» да/нет.
    4. Метрики:
       - Recall переоткрытия = (переоткрытых экспертных)/(всего экспертных)
       - Доля новых осмысленных = сколько система дала СВЕРХ экспертов, признанных
         осмысленными (валидирует эксперт-металловед вручную)
  КРИТИЧНО (правило №1): ПЕРВЫЕ матчи судьи проверь ГЛАЗАМИ — не засчитывает ли
  ложные совпадения? Синонимы нормализуй. Не доверяй судье слепо.

  ВАЖНО про обобщённость: закрытый тест жюри = 2 кейса обогащения + 2 металлургии.
  Не переобучай матчинг/промпты под обогащение. Проверь систему и на металлургическом
  примере, если найдёшь открытые данные (или отметь как риск).

СИНТЕТИЧЕСКИЙ БЕНЧМАРК (готов, проверь и подключи модель):
  Генератор синтетики + HDR-обвязка уже построены (bench/synth/). Умеют: скрытое
  правило (linear/threshold/interaction/non-monotonic) → проверка переоткрытия.
  Тест инверсии работает (инвертируешь правило — если модель говорит старое, она
  гадает). Задача: подключить зафиксированную модель, прогнать свип ≥30 правил,
  вывести HDR по уровням сложности + результат теста инверсии.

ДОКАЗАТЕЛЬНОЕ СРАВНЕНИЕ (для питча, главный тезис):
  Прогони систему НА ОДНОЙ модели в двух режимах: (а) БЕЗ grounding-слоя (B8),
  (б) С grounding. Сравни recall переоткрытия. Ожидаем: с grounding выше (наш тезис
  «слой обоснованности поднимает качество», как в TruthHypo +12%). Это ключевой
  слайд презентации.

ЗАЧЕМ: бенчмарк — фундамент доказательной базы. Без него «система хорошая» —
голословно. Доменный бенчмарк на ИХ кейсах = самый убедительный аргумент для жюри.

ПРОВЕРКА ГЛАЗАМИ: обязательна на матчинге (см. выше).
